# 용어집 — 지표와 비교 전략(arm) 라벨

이 저장소의 지표와 용어를 한 곳에서 확인하는 용어집입니다. 특히 **통과율(pass rate)** 과
**채점 커버리지(grading coverage)** 는 이름이 비슷하지만 **서로 다른 지표**입니다.

## 공통 용어

각 용어의 정의는 여기에 한 번만 둡니다. 다른 페이지는 이름만 쓰고 필요하면 이곳으로 링크합니다.

| 용어 | 정의 |
| --- | --- |
| **팬아웃 (fan-out)** | 한 태스크에 후보 모델을 한꺼번에 병렬 호출하는 방식. 승자 하나를 남기더라도 호출한 모든 후보에 비용이 발생합니다 → [실험 05](../lab-notebook/05-ensemble-fanout.md) |
| **fail-closed** | 요율 행이 없는 셀에 값을 추정해 채우지 않고, 금액을 보류한 채 그 arm의 절감 주장을 막는 규칙 → [측정 프로토콜 §6.1](measurement-protocol.md#61-v1-vs-v2) |
| **감사 원장** | 저장된 입력만으로 결정과 비용을 다시 계산할 수 있는 추가 전용(append-only) 해시 체인 실행 기록 → [감사 원장](ledger.md) |
| **플릿 (fleet)** | 배포 모델 목록(카탈로그)과 어느 모델이 어느 arm을 맡는지(역할 배정)를 묶은 설정 → [플릿](fleet.md) |
| **provenance** | 결과가 어느 경로에서 나왔는지를 가리키는 라벨. `live`(방금 일어난 실제 호출) · `recorded`(포착해 둔 실측 결과의 재생) · `test`(주입한 가짜 클라이언트) 셋 중 하나입니다 → [측정 프로토콜 §1](measurement-protocol.md) |
| **셀 (cell)** | 측정 하나의 단위. (과제 × arm × 반복) 조합이며, 실험 11·12·13은 24과제 × 4arm × n=3 = **288 계획 셀**입니다 |
| **복합 요율 (`composite-rate-card-v2`)** | 실측 Model Router 호출의 과금 방식. **라우터 input 토큰 마크업 + 라우터가 실제로 고른 백엔드의 요율**을 더해 계산합니다 |

## 실험 arm 라벨

**arm**은 같은 측정 계획으로 같은 워크로드를 비교할 때 쓰는 전략 하나를 뜻합니다.
실측 실험 11·12·13에서는 다음 네 식별자를 씁니다.

| 라벨 | 뜻 |
| --- | --- |
| `router-cost` | Model Router의 Cost 모드 |
| `router-balanced` | Model Router의 Balanced 모드 |
| `router-quality` | Model Router의 Quality 모드 |
| `direct-premium` | 프리미엄 모델 직접 호출 · `gpt-5.6-sol` |

실험 01–08의 오프라인 투영 페이지에서 `direct-premium`은 모든 태스크에 프리미엄을 쓰는
합성 기준선입니다. `gpt-5.6-sol`의 실측 성능을 뜻하지 않습니다.

!!! abstract "한눈에 — 두 지표는 다르다"
    | 지표 | 뜻 | 분모 |
    | --- | --- | --- |
    | **통과율 (pass rate)** | 통과(해결)한 태스크의 비율 | 시도한 **태스크** 수 |
    | **채점 커버리지 (grading coverage)** | 실제로 **채점된 셀**의 비율 (측정 완전성) | 계획된 **셀**(태스크 × arm × 표본 n) 수 |

    **어디서** — 통과율은 **모든 실험**에서, 채점 커버리지는 **실측 실험(11·12·13)** 에서만 씁니다.

> **핵심 한 문장.** 같은 실험에서도 **통과율**과 **채점 커버리지**는 다르게 나올 수 있습니다 —
> 오타가 아니라 **분모가 다른 별개의 지표**이기 때문입니다.

!!! tip "읽는 규칙"
    - 측정 결과(실험 11·12·13)에서 "채점된 셀 비율"을 말할 때는 항상 **채점 커버리지**로 씁니다.
      맨 이름 "커버리지"를 통과율과 나란히 두지 않습니다.
    - "통과한 태스크 비율"은 항상 **통과율**입니다.
    - 오프라인 실험·CLI의 `coverage`(=`accepted/counted`)는 **통과율**과 같은 값입니다.

??? example "예시 (실험 12 실측) — 실제 값이 궁금하면"
    개념만으로 충분하지만 구체적인 값이 궁금하면: 오프라인 실험에는 타임아웃이 없어 채점
    커버리지가 사실상 **100%**라 통과율과 일치합니다. 반면 실험 12 실측에서는 `router-cost` 가
    **통과율 95.8%(23/24)** 와 **채점 커버리지 94.4%(68/72)** 로 갈립니다 — 분모가 태스크
    **24** vs 셀 **72** 로 다르기 때문입니다. (집계 채점 커버리지·셀 정의·게이트 하한은 아래
    "용어별 정밀 정의" 참고.)

??? note "왜 두 값이 갈리나 — 오프라인은 같고, 실측은 다르다 (타임아웃 메커니즘)"
    두 지표는 **세는 단위가 다릅니다**.

    - **통과율은 태스크 단위로 셉니다** — "그 문제를 풀었나?"
    - **채점 커버리지는 셀 단위로 셉니다** — "채점할 답이 오기는 왔나?"

    오프라인 결정론 실험에는 타임아웃이 없어 모든 셀에 채점할 본문이 있으므로 채점 커버리지가
    통과율과 **일치**합니다. 오프라인 CLI가 이 값을 `coverage` 한 단어로 부르는 이유입니다.

    실측에서는 다릅니다. 한 셀이 타임아웃 나면:

    - 채점할 본문이 없어 **채점 대상에서 빠지고**(채점 커버리지 ↓, 셀 단위),
    - 그 타임아웃 때문에 해당 태스크가 끝내 통과로 수용되지 못하면 **실패로도 계상됩니다**
      (통과율 ↓, 태스크 단위).

    같은 한 번의 타임아웃이 **셀 단위**(채점 커버리지)와 **태스크 단위**(통과율)에 서로 다른
    크기로 반영되므로 두 지표는 어긋납니다.

??? note "용어별 정밀 정의 — 코드·봉인 필드"
    **통과율 (pass rate).** 시도한 태스크 중, 검증 가능한 실행 신호가 깨끗해 **통과(해결)로
    수용된** 태스크의 비율입니다. "이 arm이 문제를 실제로 얼마나 풀었나"를 답합니다.

    - **오프라인 실험(01–08).** 코드가 `coverage = accepted / counted` 로 계산합니다
      (`src/router/baseline.py`). 오프라인 CLI·실험 계약(`min_coverage`)이 출력하는 `coverage`
      필드는 **통과율과 같은 값**입니다. 실험노트의 **"통과율 절벽"**(실험 03·07 등) 서사가
      말하는 "커버리지"도 이 통과율을 뜻합니다.
    - **실측 실험(11·12·13).** 봉인 스냅샷의 `pass_rate` 필드입니다 —
      예: 실험 12의 `router-cost` 는 **23/24 = 95.8%**.

    **채점 커버리지 (grading coverage).** 한 **셀**은 (태스크 × arm × 표본)입니다 — 각 태스크·arm
    조합을 **n회 반복** 측정합니다(실험 11·12·13은 n=3). 채점 커버리지는 계획된 셀 중, 응답 본문이
    있어 **실제로 채점된 셀**의 비율입니다. 품질이나 통과 여부가 아니라 **측정이 얼마나
    완전했는가**(측정 완전성)를 답합니다.

    - **실측에서만 의미가 있습니다.** 봉인 스냅샷의 `result.grading.coverage` 필드로,
      `graded_cells / planned_cells` 입니다(`src/router/measure.py`) — 실험 12는 **24 태스크 ×
      4 arm × n=3 = 288 계획 셀**이라 집계 **277/288 = 96.18%**, arm 최저 **68/72 = 94.4%**.
    - 채점 커버리지가 낮다는 것은 "코드가 틀렸다"가 아니라 "**채점할 본문 자체가 없었다**"(예:
      타임아웃)는 뜻입니다. 그래서 품질 게이트는 채점 커버리지 하한(≥ 90%)을 따로 둡니다.

    !!! warning "봉인 스냅샷에는 `coverage`라는 이름의 필드가 **둘** 있습니다"
        같은 이름이 서로 다른 두 분수를 가리키므로 값을 인용할 때 경로까지 함께 적습니다.

        | 필드 경로 | 분수 | 실험 12 값 |
        | --- | --- | --- |
        | `result.coverage` | 채점된 셀 중 **수용된** 셀 (`accepted / graded`) | 274/277 = **98.917%** |
        | `result.grading.coverage` | 계획된 셀 중 **채점된** 셀 (`graded / planned`) | 277/288 = **96.18%** |

        품질 게이트 하한(≥ 90%)이 대는 값은 **`result.grading.coverage`**, 곧 채점 커버리지입니다.
        `result.coverage`는 분모가 이미 "채점된 셀"이라 타임아웃 손실이 분모에서 빠져 있고,
        그래서 늘 더 높게 나옵니다. 이 페이지에서 "채점 커버리지"라고 쓴 모든 자리는
        `result.grading.coverage`를 가리킵니다.

??? note "함께 자주 나오는 라벨"
    | 라벨 | 뜻 |
    | --- | --- |
    | `measured=false` (투영) | 합성 데이터에 대한 오프라인 계산. 측정된 Azure 지출이 아님(실험 01–08). |
    | `measured=true` (실측) | 실제 Azure Foundry 호출과 usage로 측정된 값(실험 09·10·11·12·13). |
    | `evidence_tier=directional` | 단일 테넌트·1회 측정의 방향성 신호. 통계적 신뢰가 아닙니다. 실험 09·10은 큐레이션 과제 5건, 실험 11·12·13은 24과제 × 4arm × n=3 = 288 계획 셀로, 다섯 실험 모두 이 등급입니다. |
    | `cost_complete=true` / `unpriced 0%` | 모든 셀이 고정 요율로 가격화됨. |
    | `plan_hash` | 워크로드·정책·요율을 봉인한 내용 주소 해시. 재현·재생의 기준. |
    | `03D` | 실험 11·12·13을 묶어 부르는 저장소 내부 계열 라벨. 파일명·아티팩트 경로에만 남고 본문에서는 실험 번호로 씁니다. |

    각 수치의 정직 라벨(measured/projected)은 **해당 페이지에서** 확인하세요 — 이 용어집은 이름과
    정의만 통일할 뿐, 페이지별 주장 경계를 대체하지 않습니다. 경계 전반은
    [정직함 규약](../honesty.md)을 참고하세요.
