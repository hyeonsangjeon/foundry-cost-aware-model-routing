# 핵심 개념

## 문제

여러 모델을 쓸 수 있는 개발 도구도 계획·코드 생성·테스트 생성·검증을 같은 프리미엄 모델에
보내면 **싱글 모델처럼 지출**합니다. 앞에서는 코딩 에이전트를 쓰더라도 뒤에서는 API 호출
비용을 냅니다. 이 방식이 낭비가 되는 이유는 두 가지입니다.

1. **모든 것을 가장 잘하는 단일 모델은 없다.** 태스크 유형마다 잘하는 모델이 다르고 해결당
   비용(`$/resolved`)도 모델에 따라 자릿수 단위로 달라집니다.
2. **대부분의 태스크는 최상위 모델이 필요 없다.** 더 싼 후보도 상당수를 첫 시도에 풉니다.

## 논지

모든 태스크에 같은 모델을 쓰지 않고 태스크마다 모델을 고릅니다.

- **가장 싼 후보**부터 시작합니다.
- 결과를 검사합니다. 적용됨·컴파일됨·자체 테스트 통과·린트/타입 통과처럼 **검증 가능한 자체
  신호가 깨끗할 때만** 수용하며 느낌으로 판단하지 않습니다.
- 검사에 실패하면 다음 후보나 실행 채점 기반의 소규모 **앙상블**로 **에스컬레이션**합니다.
- 여러 모델을 부르기 전에 **비용 거버너**가 추가 지출을 할 만한 태스크인지 판단합니다.

여기서 **통과율(pass rate)** 은 해결한 태스크의 비율입니다. 오프라인 CLI·실험 계약은 이 필드를
`coverage`로 부릅니다. 실측 결과에는 답이 도착해 실제로 채점할 수 있었던 셀의 비율인 **채점
커버리지**도 따로 나옵니다. 둘은 다른 지표입니다([용어집](glossary.md)). 목표는
"가능한 가장 싼 청구서"가 아닙니다. **같은 통과율을 훨씬 낮은 비용으로 내고 모든 결정에 감사
추적을 남기는 것**입니다.

!!! quote "이 프로젝트가 답하는 오래된 현장 우려"
    "멀티 모델 방식은 사용 사례가 추가 토큰과 지연을 정당화할 때만 가치가 있다."
    — **비용 거버너**는 지출 전에 이 조건을 코드로 확인합니다.

!!! info "내장 Model Router는 이미 잘 합니다 — 이 저장소는 그 위의 '보완층'"
    Azure AI Foundry **내장 Model Router**는 프롬프트를 읽고 어떤 모델을 부를지 예측해
    **모델 선택**을 처리합니다. 배포 하나가 OpenAI(GPT-4/5 계열), xAI Grok, DeepSeek, Meta
    Llama, gpt-oss로 **별도 배포 없이 크로스 프로바이더** 라우팅합니다. Anthropic Claude만 직접
    배포가 필요합니다([실험 07](../lab-notebook/07-model-router.md)).

    내장 라우터가 이미 *"여러 회사 모델을 라우팅한다"*는 일을 맡습니다. 이 저장소는 내장
    라우터가 고른 결과부터 처리합니다. 라우터를 **대체(replace)**하지 않고
    **보완(complement)**합니다. 다음 단계는 별개입니다. ① 실행 신호로 결과를 **검증**하고 깨끗할
    때만 수용합니다 · ② 실패하면 **에스컬레이션**합니다 · ③ 앙상블의 추가 지출이 필요한지 **비용
    거버너**로 판단합니다 · ④ 모든 결정을 해시체인·비용재생이 가능한 **감사 원장**에 남깁니다.
    넷 다 이 저장소에 **구현돼 있습니다**. 쿼터·라우팅·관측을 게이트웨이에서 처리하는 **APIM
    거버넌스**는 그다음 확장 방향입니다.

    내장 Model Router도 **일급 후보 arm(`single_call`)**으로 남습니다. 이 프로젝트는 제품을
    대체하지 않고 사용합니다.

    > **한 줄:** 모델 선택은 내장 Model Router가 이미 잘 합니다. 이 자산은 그 **다음 문제** —
    > 선택된 결과를 **검증**하고, 실패를 **에스컬레이션**하고, 멀티모델 지출을 **거버닝**하고,
    > 결정을 **감사 가능**하게 만드는 층입니다.

## 네 개의 결정 계층

```text
1. CLASSIFY  태스크 → {plan, generate, test, validate, repo_patch}
2. POLICY    태스크 클래스 → 순위가 매겨진 후보 모델 (pass-rate, $/resolved 사전값)
3. SELECT    비용 인지 단일 경로(가장 싼-깨끗한-우선); 실패 시 실행 채점 앙상블 + 심판 타이브레이크
4. GOVERN    추론 강도 조절 · PTU vs PAYG · 429 retry-after · 프롬프트 캐시 버킷팅 (지출 전 게이트)
```

### 1 · Classify
가벼운 분류기가 들어온 태스크를 클래스에 넣습니다. '작은 함수 생성'과 '레포지토리 패치'는
필요한 모델과 지출 상한이 다를 수 있습니다. 처음에는 키워드·메타데이터·diff 크기 같은 규칙을
쓰고 나중에 소형 모델로 바꿀 수 있습니다.

### 2 · Policy
각 클래스에는 순서가 있는 후보 모델 목록이 있습니다. 후보마다 두 시작값을 둡니다.
**pass-rate**는 그 클래스를 얼마나 자주 해결하는지, **`$/resolved`**는 해결당 총비용입니다.
공개·현장 벤치마크로 처음 값을 정하고 **여러분의 라우팅 텔레메트리로 갱신**합니다. 고정된
진리가 아니라 운영 정책입니다.

시드 정책은 [`src/policy/seed_policy.yaml`](https://github.com/hyeonsangjeon/foundry-cost-aware-model-routing/blob/main/src/policy/seed_policy.yaml)에 있고
계약(모든 클래스 존재, `prior_usd_resolved` 비내림차순 정렬 등)은 `PolicyTable.validate`가 강제합니다.

### 3 · Select
거버너는 두 방법 중 하나를 고릅니다.

- **비용 인지 단일 경로** — 가장 싼 후보부터 시도합니다. 검증 가능한 신호가 깨끗한 첫 결과를
  수용하고 실패한 경우에만 상위 후보로 옮깁니다. 대부분의 절감이 이 경로에서 나옵니다.
- **실행 기반 앙상블** — 여러 후보를 실행 신호로 검사하고 동점은 LLM 심판으로 가릅니다.
  통과율을 높일 수 있지만 비용도 늘어나므로 거버너가 고가치로 표시한 태스크에만 씁니다.

### 4 · Govern
비용 거버너는 지출 전에 태스크가 쓸 작업량을 정합니다. 추론 강도, PAYG vs 프로비저닝 처리량,
`429 retry-after-ms` 수용 신호 처리, `prompt_cache_key` 버킷팅을 조절합니다. 라우터는 이 계층을
동반 툴킷의 **의존성**으로 사용하며 그 수학을 다시 구현하지 않습니다.

## 왜 '가장 싼 청구서'가 정답이 아닌가

히어로 실험은 합성 100건을 단일 호출 arm과 비용 인지 라우팅으로 실행합니다.

| arm | 선택 방식 | 통과율 | 비용 |
| --- | --- | --- | --- |
| cost | 클래스별 가장 싼 후보 | **22%** | $0.19 |
| balanced | 클래스별 중간 후보 | 38% | $1.32 |
| quality (naive) | 클래스별 가장 비싼 후보 | 100% | $2.23 |
| **비용 인지 라우팅** | 통과하는 가장 싼 모델 먼저 | **100%** | **$1.66** |

가장 싼 arm은 태스크의 22%만 풉니다. 프리미엄 arm은 100%를 풀지만 비용이 가장 큽니다.
라우팅은 싼 모델부터 시작해 검사에 실패하면 상위 모델로 옮깁니다. 이 방식도 **통과율 100%를
유지하면서** 나이브 대비 25.5% 낮은 비용을 냅니다([오프라인 실험 결과](projection-results.md)가 정본).

!!! note "이 표는 예시용 등가물입니다"
    cost/balanced/quality arm은 투명한 **자리표시자 baseline**이며 관리형 라우터의 내부 구현에
    대한 주장이 아닙니다. 모든 수치는 `labels.measured = false` — 실제 호출 없이 만든 오프라인
    투영이라는 뜻입니다.

## 주장 권한 라벨

이 저장소의 모든 수치·행위 주장은 권한 라벨을 유지합니다.

- **Tier 1 — 벤더 스펙.** 예: `retry-after-ms` 수용 신호, 문서화된 캐시 키 임계값, 공개 요율.
- **Tier 2 — 이 프로젝트의 추론/운영 정책.** 예: 시드 pass-rate/`$/resolved` 사전값,
  에스컬레이션 임계값, "값 X 이상에서만 앙상블" 규칙.

오프라인 before/after는 **합성 데이터에 대한 투영**이며 측정된 절감이 아닙니다. 여러분의
워크로드에서 **측정된** 절감은 여러분의 테넌트에서 라이브 eval을 돌려야 나옵니다.

자세한 경계는 [정직함 규약](../honesty.md)을 참고하세요.
