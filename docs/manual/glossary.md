# 용어집 — 통과율 vs 채점 커버리지

이 저장소의 지표를 한 곳에서 확인하는 용어집입니다. 특히 **통과율(pass rate)** 과
**채점 커버리지(grading coverage)** 는 이름이 비슷하지만 **서로 다른 지표**입니다.

!!! abstract "한눈에 — 두 지표는 다르다"
    | 지표 | 뜻 | 분모 | 어디서 |
    | --- | --- | --- | --- |
    | **통과율 (pass rate)** | 통과(해결)한 태스크의 비율 | 시도한 **태스크** 수 | 모든 실험 · 03D |
    | **채점 커버리지 (grading coverage)** | 실제로 **채점된 셀**의 비율 (측정 완전성) | 계획된 **셀**(태스크 × arm × 표본 n) 수 | 실측 실험(11·12·03D)만 |

> **핵심 한 문장.** 03D의 `router-cost` 는 **통과율 95.8%(23/24)** 와 **채점 커버리지
> 94.4%(68/72)** 로 갈립니다 — 오타가 아니라 정의가 다른 별개의 값입니다.

!!! tip "읽는 규칙"
    - 측정 결과(11·12·03D)에서 "채점된 셀 비율"을 말할 때는 항상 **채점 커버리지**로 씁니다.
      맨 이름 "커버리지"를 통과율과 나란히 두지 않습니다.
    - "통과한 태스크 비율"은 항상 **통과율**입니다.
    - 오프라인 실험·CLI의 `coverage`(=`accepted/counted`)는 **통과율**과 같은 값입니다.

??? note "왜 두 값이 갈리나 — 오프라인은 같고, 실측은 다르다 (타임아웃 메커니즘)"
    두 지표는 **분모가 다릅니다**(태스크 vs 셀). 그래서:

    - **오프라인 결정론 실험에는 타임아웃이 없어** 모든 셀이 채점되므로 채점 커버리지가 사실상
      100%이고, 통과율과 수치가 **일치**합니다. 오프라인 CLI가 통과율을 `coverage` 한 단어로
      부르는 이유입니다.
    - **실측에서는 타임아웃 셀이 생깁니다.** 타임아웃 셀은 채점할 본문이 없어 **채점 커버리지
      분자에서 빠지고**(셀 단위), 그 타임아웃이 해당 태스크를 끝내 통과로 수용되지 못하게 만들면
      **통과율에서도 실패**가 됩니다(태스크 단위). 두 지표가 **분모도 단위도 다르게**(셀 72 vs
      태스크 24) 같은 타임아웃에 반응하므로, 03D의 `router-cost` 는 **통과율 95.8%(23/24)** 와
      **채점 커버리지 94.4%(68/72)** 로 갈립니다 — 오타가 아니라 정의가 다른 별개의 값입니다.

??? note "용어별 정밀 정의 — 코드·봉인 필드"
    **통과율 (pass rate).** 시도한 태스크 중, 검증 가능한 실행 신호가 깨끗해 **통과(해결)로
    수용된** 태스크의 비율입니다. "이 arm이 문제를 실제로 얼마나 풀었나"를 답합니다.

    - **오프라인 실험(01–08).** 코드가 `coverage = accepted / counted` 로 계산합니다
      (`src/router/baseline.py`). 즉 오프라인 CLI·실험 계약(`min_coverage`)이 출력하는 `coverage`
      필드는 **통과율과 같은 값**입니다. 실험노트의 **"커버리지 절벽"**(실험 03·07 등) 서사가
      말하는 "커버리지"도 이 통과율을 뜻합니다.
    - **실측 실험(03D).** 봉인 스냅샷의 `pass_rate` 필드입니다 —
      예: `router-cost` 는 **23/24 = 95.8%**.

    **채점 커버리지 (grading coverage).** 한 **셀**은 (태스크 × arm × 표본)입니다 — 각 태스크·arm
    조합을 **n회 반복** 측정합니다(03D는 n=3). 채점 커버리지는 계획된 셀 중, 응답 본문이 있어
    **실제로 채점된 셀**의 비율입니다. 품질이나 통과 여부가 아니라 **측정이 얼마나 완전했는가**
    (측정 완전성)를 답합니다.

    - **실측에서만 의미가 있습니다.** 봉인 스냅샷의 `coverage` 필드(`basis: graded`)로,
      `graded_cells / planned_cells` 입니다 — 03D는 **24 태스크 × 4 arm × n=3 = 288 셀**이라 집계
      **277/288 = 96.18%**, arm 최저 **68/72 = 94.4%**.
    - 채점 커버리지가 낮다는 것은 "코드가 틀렸다"가 아니라 "**채점할 본문 자체가 없었다**"(예:
      타임아웃)는 뜻입니다. 그래서 품질 게이트는 채점 커버리지 하한(≥ 90%)을 따로 둡니다.

??? note "함께 자주 나오는 라벨"
    | 라벨 | 뜻 |
    | --- | --- |
    | `measured=false` (투영) | 합성 데이터에 대한 오프라인 계산. 측정된 Azure 지출이 아님(실험 01–08). |
    | `measured=true` (실측) | 실제 Azure Foundry 호출과 usage로 측정된 값(실험 09·10·11·12). |
    | `evidence_tier=directional` | 24 과제·단일 테넌트·1회 측정 — 통계적 신뢰가 아니라 방향성 신호. |
    | `cost_complete=true` / `unpriced 0%` | 모든 셀이 고정(pinned) 요율로 가격화됨. |
    | `plan_hash` | 워크로드·정책·요율을 봉인한 내용 주소 해시. 재현/replay의 기준. |

    각 수치의 정직 라벨(measured/projected)은 **해당 페이지에서** 확인하세요 — 이 용어집은 이름과
    정의만 통일할 뿐, 페이지별 주장 경계를 대체하지 않습니다. 경계 전반은
    [정직함 규약](../honesty.md)을 참고하세요.
